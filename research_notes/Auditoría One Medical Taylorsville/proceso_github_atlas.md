## 1. What ChatGPT Atlas is (and was), its current status in October 2026, and what it could and could not do for a clinic website on GitHub

### Takeaway
ChatGPT Atlas was OpenAI's AI-native browser. It launched on macOS on 2025-10-21 and was **shut down on 2026-08-09**. It never shipped for Windows, iOS or Android. As of today (2026-10-20), a "GitHub + ChatGPT Atlas" process cannot be running as described. Its agentic browsing moved into the new ChatGPT desktop app (with a built-in browser and the "ChatGPT Work" agent), a ChatGPT browser extension, and Codex. The same risk profile carries over to those tools. Even at its peak, Atlas agent mode could only drive web UIs by clicking and typing. It could not run code, download files or touch the local file system, so it could not build, test or check a website.

### Cited Findings
**Launch, platforms, plans**
- [CONFIRMED] OpenAI released Atlas for macOS on 2025-10-21 and said Windows, iOS and Android would follow. Atlas itself was open to Free, Plus, Pro and Go users. **Agent mode was a preview limited to Plus, Pro and Business** (Business described by some as an admin-enabled beta). — [OpenAI: Introducing ChatGPT Atlas](https://openai.com/blog/introducing-chatgpt-atlas); [TechRadar](https://techradar.com/ai-platforms-assistants/chatgpt/openai-launched-a-chatgpt-atlas-browser-here-are-the-5-things-you-need-to-know); [The Decoder](https://the-decoder.com/openai-launches-atlas-a-new-web-browser-built-around-chatgpt-integration/)
- [REPORTED] The macOS build required Apple Silicon (M1 or later) and macOS 14 or later. Sources differ on the minimum version: one says 14, another 14.2. — [Wikipedia: ChatGPT Atlas](https://en.wikipedia.org/wiki/ChatGPT_Atlas); [TechSpot download page](https://www.techspot.com/downloads/7801-openai-atlas.html)
- [CONFIRMED] Launch features: a ChatGPT sidebar on any page, opt-in "browser memories", and agent mode. OpenAI says browser memories store "facts and insights" from browsing, not full page content. — [OpenAI Help: Atlas browser memories](https://help.openai.com/en/articles/12574210-chatgpt-atlas-browser-memories); [OpenAI launch post](https://openai.com/blog/introducing-chatgpt-atlas)
- [REPORTED] Agent mode could open tabs, click through pages and carry out multi-step tasks such as shopping or filling in forms. It asked before important actions, and the user could pause it or take over. — [TechRadar](https://techradar.com/ai-platforms-assistants/chatgpt/openai-launched-a-chatgpt-atlas-browser-here-are-the-5-things-you-need-to-know)

**Windows status and the shutdown (2026)**
- [CONFIRMED by several outlets] Atlas never shipped for Windows, iOS or Android, not even as a public beta, before it was switched off. A Metaculus question, "Will Atlas be released for Windows before September 1, 2026?", showed about a 4% forecast when captured. — [Wikipedia](https://en.wikipedia.org/wiki/ChatGPT_Atlas); [Metaculus](https://www.metaculus.com/questions/43525/will-atlas-browser-be-released-for-windows-before-september-1-2026/); [ToolDirectory: shut down Aug 9, 2026](https://tooldirectory.ai/tools/chat-gpt-atlas)

OpenAI's help article is titled "Evolving Atlas into ChatGPT for browser-based agentic work". It says the capabilities are moving into ChatGPT and Codex, tells users to export bookmarks before the cutoff, and points admins to the ChatGPT desktop app and the ChatGPT Chrome extension or sidebar. — [OpenAI Help 20001371](https://help.openai.com/en/articles/20001371); [TechRepublic](https://www.techrepublic.com/article/news-chatgpt-atlas-shutdown-migration/); [9to5Mac, 2026-08-04](https://9to5mac.com/2026/08/04/openai-explains-what-will-happen-when-chatgpt-atlas-shuts-down-this-weekend/); [The Next Web](https://thenextweb.com/news/openai-chatgpt-atlas-browser-shutdown-superapp); [Tom's Guide](https://www.tomsguide.com/ai/openai-is-shutting-down-its-ai-browser-but-chatgpt-users-are-getting-something-better); [Mac Observer](https://www.macobserver.com/news/chatgpt-atlas-browser-is-shutting-down-openai-confirms/)
- [REPORTED] The replacement is a ChatGPT desktop "super app" launched 2026-07-09 for macOS and Windows that combines Chat, Work and Codex. A Linux preview reportedly followed on 2026-08-14. Its Work mode includes a built-in browser that handles tabs, downloads, navigation and logging into accounts. A separate ChatGPT extension covers Chrome, Edge, Brave, Opera and Vivaldi. — [AI Weekly](https://aiweekly.co/alerts/openai-sunsets-chatgpt-atlas-folds-browser-into-desktop-app); [PPC Land](https://ppc.land/openai-kills-atlas-browser-folds-it-into-new-chatgpt-work-agent/); [Medium (Adi Leviim)](https://medium.com/@adi_leviim/openai-shut-down-its-browser-now-chatgpt-wants-to-live-inside-yours-c81784492e59); [Medium (AI Actually)](https://medium.com/ai-actually/chatgpt-atlas-is-gone-here-is-what-actually-replaced-it-3e1b8091f5d5)

**Documented limitations of agent mode**
- [CONFIRMED] OpenAI's help article says Atlas agent mode **cannot run code in the browser, download files or install extensions, and cannot access other apps on the computer or the file system**. — [OpenAI Help: Atlas agent mode](https://help.openai.com/en/articles/12628199-chatgpt-atlas-agent-mode)
- [CONFIRMED] "Watch mode" pauses the agent on certain sensitive sites, such as financial institutions, unless the user is watching the tab. "Logged-out mode" runs the agent without existing cookies and without signing into accounts unless the user approves. — [OpenAI Help: Atlas agent mode](https://help.openai.com/en/articles/12628199-chatgpt-atlas-agent-mode); [Simon Willison quoting OpenAI CISO Dane Stuckey, 2025-10-22](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)
- [CONFIRMED, opinion] At launch, Simon Willison wrote that the main defense seemed to be expecting the user to watch closely everything agent mode does. — [Simon Willison, 2025-10-21](https://feeds.simonwillison.net/2025/Oct/21/introducing-chatgpt-atlas/)
- [REPORTED] A third-party guide says the agent could not read or write ChatGPT memories, saved passwords or autofill data. — [Routine blog](https://open.routine.co/blog/posts/chatgpt-agent-use-cases)
- [REPORTED] Gartner lists "inaccurate reasoning-driven erroneous agent actions" alongside prompt injection as a core risk of AI browsers. — [The Register](https://www.theregister.com/2025/12/08/gartner_recommends_ai_browser_ban/)

### Inferences
- [INFERRED] **Status for the report:** if the clinic still describes its process as "GitHub + ChatGPT Atlas", the process is either out of date (stopped on 2026-08-09) or has quietly moved to the ChatGPT desktop app's Work browser, the ChatGPT Chrome extension, or Codex. Each has a different risk profile. The audit should ask which tool they use now. Any bookmarks, saved logins or cookies left in Atlas were lost unless exported.
- [INFERRED] **What Atlas could actually do on GitHub:** since agent mode could not run code, download files or touch the file system, it could only work GitHub through the web UI. That means editing files in the browser editor, writing commit messages, opening or merging PRs, and changing repository settings, Pages settings and secrets pages by clicking. It could not run `npm build`, check that an Astro/Jekyll build passes, run accessibility or link checks, or preview locally. A change would be "tested" only when it went live, unless GitHub Actions or a preview environment was already set up.
- [INFERRED] The same goes for website builders (Wix, Squarespace, Google Business Profile editors). The agent fills in forms in a logged-in admin UI, which is exactly where logged-in prompt-injection risk is highest (see Q2).
- [INFERRED] Because Atlas was macOS and Apple Silicon only, clinic staff on Windows front-desk PCs could never have used it. Only someone on a recent Mac could.
- [INFERRED] Codex is OpenAI's coding agent ([Wikipedia: Codex](https://en.wikipedia.org/wiki/Codex_(AI_agent))). It is a far better fit for repository work than a browser agent, because it edits code and opens PRs. That is still unreviewed AI-written code unless a human reviews the PR.

### Gaps
- I found no first-hand account or tutorial of a clinic or small business using Atlas specifically to edit a GitHub repo or website builder. The search for "Atlas agent mode GitHub" returned unrelated products (Arena Agent Mode, other projects named "Atlas"). How people used it for this remains anecdotal.
- I could not confirm, from an OpenAI primary page, whether ChatGPT Work's built-in browser keeps Atlas's limits (no code execution, no downloads). Secondary sources say it does handle downloads.
- Exact plan eligibility for agent features in the ChatGPT desktop app or Work (Oct 2026) was not confirmed.

## 2. Security research on Atlas and agentic browsers, mitigations, and the risk of using one while logged into GitHub, the registrar, Google Business Profile or patient systems

### Takeaway
Within days of launch (Oct 2025), several independent research groups showed that Atlas and other AI browsers can be hijacked by content on web pages: LayerX with CSRF memory poisoning, NeuralTrust with omnibox injection, and Brave across the whole category. In December 2025 OpenAI said publicly that prompt injection is "unlikely to ever be fully 'solved'", and Gartner told enterprises to block AI browsers. The agent acts with the user's logged-in sessions. So an agent driving the clinic's GitHub, domain registrar, Google Business Profile or EHR can be steered by one malicious page into defacing the site, hijacking DNS, changing listings or leaking patient data.

### Cited Findings
- [CONFIRMED / vendor research] **LayerX (Oct 2025), CSRF memory poisoning:** a malicious page can use a cross-site request, riding on the victim's existing ChatGPT login, to write hidden instructions into ChatGPT memory. Those instructions fire later during normal use, and researchers said they could trigger code fetches, privilege escalation or data exfiltration. LayerX also reported that Atlas blocked only **5.8%** of malicious pages in its tests and that users were up to **90% more exposed** than on Chrome or Edge. These are vendor-reported numbers, and technical details were withheld. — [The Hacker News, Oct 2025](https://thehackernews.com/2025/10/new-chatgpt-atlas-browser-exploit-lets.html); [LayerX](https://layerxsecurity.com/?p=3863)
- [CONFIRMED / vendor research] **NeuralTrust (Oct 2025), omnibox prompt injection:** a malicious prompt dressed up as a URL in Atlas's combined address/command bar could be read as a trusted user command. It could tell the agent to open attacker sites or take harmful actions on logged-in sites such as Google Drive. OpenAI was notified and began working on mitigations. — [ITPro](https://itpro.com/security/cyber-researchers-have-already-identified-several-big-security-vulnerabilities-on-openais-atlas-browser); [SC World via Slashdot, 2025-11-01](https://tech.slashdot.org/story/25/11/01/054213/)
- [CONFIRMED] **Brave (Oct 2025):** indirect prompt injection is "not an isolated issue, but a systemic challenge facing the entire category of AI-powered browsers." Brave showed instructions hidden in screenshots (faint light-blue text on yellow) that Perplexity Comet read and executed, plus white-on-white text, HTML comments and near-invisible text in images. Brave warned that if you are signed into your bank or email, "simply summarizing a Reddit post could result in an attacker being able to steal money or your private data." Note: Brave's demos targeted Comet, Fellou and Opera Neon, not Atlas specifically. — [Brave](https://brave.com/blog/unseeable-prompt-injections/); [Simon Willison, 2025-10-21](https://simonwillison.net/2025/Oct/21/unseeable-prompt-injections/)
- [CONFIRMED] **OpenAI (Dec 2025):** OpenAI's post on hardening Atlas says prompt injection is "unlikely to ever be fully 'solved'" and that agent mode "expands the security threat surface." It announced an adversarially trained model and stronger safeguards after automated red-teaming found a new class of attacks, and said it is "optimistic" about reducing risk over time. — [Fortune, 2025-12-23](https://www.fortune.com/2025/12/23/openai-ai-browser-prompt-injections-cybersecurity-hackers); [The Decoder](https://the-decoder.com/openai-admits-prompt-injection-may-never-be-fully-solved-casting-doubt-on-the-agentic-ai-vision/); [Techloy](https://www.techloy.com/openai-admits-prompt-injection-isnt-going-away-as-it-hardens-security-for-atlas/)
- [CONFIRMED] **OpenAI CISO guidance (2025-10-22):** use **logged-out mode** where possible. "Logged-in mode" is "most appropriate for well-scoped actions on very trusted sites." Watch mode pauses the agent on sensitive sites when you leave the tab. — [Simon Willison quoting Dane Stuckey](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)
- [CONFIRMED, existence only] OpenAI has published "Understanding prompt injections: a frontier security challenge" and a post introducing "Lockdown Mode and Elevated Risk labels" in ChatGPT. I could not retrieve their contents or dates. — [OpenAI: prompt injections](https://openai.com/index/prompt-injections/); [OpenAI: Lockdown Mode](https://openai.com/index/introducing-lockdown-mode-and-elevated-risk-labels-in-chatgpt/)
- [CONFIRMED] **Gartner (Dec 2025)**, research note "Cybersecurity Must Block AI Browsers for Now" by Dennis Xu, Evgeny Mirolyubov and John Watts: block AI browsers such as Comet and Atlas "for the foreseeable future". The risks it names are indirect-prompt-injection-induced rogue agent actions, erroneous agent actions, loss and abuse of credentials, and corporate data sent to cloud AI services, with possible "irreversible and untraceable" data loss. It notes that default settings put user experience ahead of security. — [The Register, 2025-12-08](https://www.theregister.com/2025/12/08/gartner_recommends_ai_browser_ban/); [CSO Online](https://www.csoonline.com/article/4102571/keep-ai-browsers-out-of-your-enterprise-warns-gartner-2.html); critique: [Security Boulevard](https://securityboulevard.com/2025/12/gartners-ai-browser-ban-rearranging-deck-chairs-on-the-titanic/)
- [CONFIRMED / secondary summaries] **OWASP Top 10 for Agentic Applications 2026** (OWASP GenAI Security Project, Dec 2025): **ASI01 Agent Goal Hijack** covers instructions hidden in web pages or documents that change the agent's objective while its actions still look legitimate. The control is to treat runtime external content as untrusted. **ASI02 Tool Misuse** covers a legitimate tool (file write, API call) used with unauthorized parameters. The controls are least-agency scoping, parameter validation, and approval gates for irreversible actions. — [HUMAN Security](https://www.humansecurity.com/learn/blog/owasp-top-10-agentic-applications/); [Cycode](https://cycode.com/blog/owasp-top-10-agentic-applications/); [AI Governance Library](https://www.aigl.blog/owasp-top-10-for-agentic-applications-2026/)
- [REPORTED] **Successor products (2026):** a practitioner guide lists ChatGPT Work's use of the browser and signed-in sessions as high-risk. It recommends turning it off by default and approving it per app, site and use case. A separate analysis reports that once a user allows a site, the documentation describes no separate confirmation before the agent edits a record or sends a message there, and no full action log. — [Harmonic Security](https://www.harmonic.security/resources/securing-chatgpt-work-a-practitioners-guide); [Beri.net](https://www.beri.net/article/chatgpt-chrome-extension-work-mode-computer-use-logged-in-tabs-enterprise-admin-controls-allowlist-no-action-log); [NeuralTrust: ChatGPT agent security](https://neuraltrust.ai/blog/chatgpt-agent-security)

### Inferences
- [INFERRED] **Threat model for a clinic** (one browser profile logged into everything):
  - **GitHub** (push or admin): an injected instruction could commit a malicious script (card skimmer, redirect, fake "pay here" form) or change the Pages custom domain. It could also add a collaborator or deploy key, or switch off push protection. Without branch protection (Q4), the change goes straight to production.
  - **Domain registrar / DNS**: changing nameservers or MX records, unlocking or transferring the domain. That means site and email takeover, and losing the domain is the hardest damage to undo.
  - **Google Business Profile**: changing the phone number, website link or hours. Patients' calls get diverted, a reputation and safety problem for a medical practice.
  - **EHR / patient portal / practice-management system**: reading PHI from the screen and sending it out through a URL the agent visits or a form it fills in. Combined with a missing BAA (Q3), this is a reportable-breach risk.
- [INFERRED] **Mitigations for anyone who still uses an agentic browser:**
  - Use a separate browser or profile that is never signed into GitHub, the registrar, GBP, EHR, banking or email.
  - Use logged-out mode by default, and watch every logged-in action.
  - Never let the agent run on pages that hold patient data.
  - Turn browser memories off.
  - Use hardware-key or app 2FA so a hijacked session can't easily add new credentials.
  - Lock the registrar and turn on DNSSEC.
  - Use least-privilege GitHub tokens or roles, so the account the agent runs as can open PRs but cannot merge or change settings.

  These follow the OpenAI CISO, Gartner and OWASP guidance above.
- [INFERRED] The core design conflict (the agent reads untrusted pages while holding the user's authenticated sessions) is the same in Atlas, the ChatGPT Work browser and Chrome-extension agents. The shutdown does not remove the risk. It moves it.

### Gaps
- I found no public confirmation of whether OpenAI fully fixed the LayerX CSRF/memory issue or the NeuralTrust omnibox issue before the shutdown.
- I found no documented incident in which an AI browser agent defaced a small-business site or hijacked a domain. The risk is shown in research, not in public incident reports I could find.

## 3. Privacy and PHI: BAA availability, training defaults, and what it means if staff browse EHR or patient portals in Atlas or its successors

### Takeaway
OpenAI does **not** offer a BAA for consumer ChatGPT (Free, Plus, Pro) or ChatGPT Business, according to multiple compliance sources. BAAs are limited to sales-managed Enterprise/Edu, zero-retention API, and the newer healthcare offerings. On consumer plans, chats are used for training by default. Atlas's separate "Include web browsing" training toggle was off by default. OpenAI's own Atlas-for-Enterprise page said Atlas was early access, outside SOC 2 and ISO scope, and that browsing data, memories and agent activity might not follow enterprise retention and deletion controls. A clinic employee browsing an EHR or patient portal in Atlas (or a successor agent browser) on a Plus or Business account would be exposing PHI to a vendor with no BAA. That is a likely HIPAA impermissible disclosure.

### Cited Findings
- [CONFIRMED] **Atlas training controls:** the "Include web browsing" toggle "controls whether the content you browse in ChatGPT Atlas can be used to train our models. This toggle is off by default." The chat-training setting is separate. If it is on, Atlas chats (including any browser-memory context used in them) can be used for training. — [OpenAI Help: Atlas data controls and privacy](https://help.openai.com/en/articles/12574142-chatgpt-atlas-data-controls-and-privacy)
- [CONFIRMED] **Consumer default:** on personal Free, Plus and Pro workspaces, "data sharing is enabled for you by default". Users opt out under Settings > Data Controls > "Improve the model for everyone". With ChatGPT Business, Enterprise, Edu and the API, OpenAI says it does not train on inputs or outputs by default. — [OpenAI Help: How do I disable model training](https://help.openai.com/en/articles/8983130-how-do-i-disable-model-training)
- [REPORTED] Opting out only applies going forward. It does not delete past conversations or remove data already used in training. — [TechRadar](https://www.techradar.com/computing/artificial-intelligence/your-chatgpt-data-automatically-trains-its-ai-models-unless-you-turn-off-this-setting); [meprism](https://meprism.com/opt-out-guides/blog/chatgpt-openai-ai-training-opt-out)
- [CONFIRMED] **Atlas for Enterprise page:** Atlas for Business and Enterprise is "early access", and OpenAI recommends "caution using Atlas in contexts that require heightened compliance and security controls". Workspace controls do not automatically apply to Atlas unless the page lists them. The translated versions (German, Portuguese) say outright that Atlas is **outside the scope of OpenAI's SOC 2 and ISO attestations**. Browsing data, browser memories and agent activity may not be covered by enterprise retention, storage, segregation or deletion requirements. **Atlas was on by default for all Business workspaces with no admin opt-in**, and off by default for Enterprise. — [OpenAI Help: Atlas for Enterprise (EN)](https://help.openai.com/en/articles/12603091-chatgpt-atlas-for-enterprise); [DE version](https://help.openai.com/de-de/articles/12603091-chatgpt-atlas-for-enterprise); [PT-BR version](https://help.openai.com/pt-br/articles/12603091-chatgpt-atlas-for-enterprise)
- [REPORTED, consistent across sources] **BAA availability:** no BAA for Free, Plus or Pro, and no BAA for ChatGPT Business (one source cites OpenAI's help center on this). Sales-managed ChatGPT Enterprise or Edu customers may request a BAA. Sources disagree on scope: one says only "ChatGPT for Enterprise with Regulated Workspace", another says Zero-Retention API plus ChatGPT Enterprise. For the API, the BAA covers only zero-retention-eligible endpoints. OpenAI launched "ChatGPT for Healthcare" on 2026-01-08, listed as HIPAA-eligible. A signed BAA covers OpenAI's obligations, not the clinic's own. — [AccountableHQ](https://www.accountablehq.com/post/is-chatgpt-hipaa-compliant-what-you-need-to-know-about-phi-and-baas); [AccountableHQ (OpenAI)](https://www.accountablehq.com/post/is-openai-hipaa-compliant-current-status-baas-and-secure-alternatives); [IntuitionLabs](https://intuitionlabs.ai/articles/is-chatgpt-hipaa-compliant); [Medcurity](https://medcurity.com/is-chatgpt-hipaa-compliant/)
- [CONFIRMED / law-firm sources] **HHS tracking-technology guidance (relevant to analytics on the clinic site):**
  - 2022-12-01: OCR guidance said an IP address combined with a visit to an unauthenticated public page about health conditions or providers could be PHI.
  - 2024-03-18: revised guidance added a user-intent test.
  - 2024-06-20: in *AHA v. Becerra* (N.D. Tex.) the court **vacated the guidance to the extent** it said HIPAA applies when tracking connects an IP address with a visit to an unauthenticated public page.
  - 2024-08-29: HHS dropped its appeal.

  — [Morrison Foerster](https://mofo.com/resources/insights/240930-a-mofo-privacy-minute-q-a-hhs-withdraws); [Holland & Hart](https://www.hollandhart.com/court-vacates-hipaa-on-line-tracking-guidance); [ABA Health Law](https://www.americanbar.org/groups/health_law/news/2024/09/hhs-voluntarily-dismisses-appeal-online-tracking-technology-lawsuit/); [Mondaq](https://www.mondaq.com/unitedstates/healthcare/1486402/federal-judge-vacates-key-points-of-hhs-ocr-hipaa-online-tracking-technology-guidance)

### Inferences
- [INFERRED] **No Atlas-specific BAA ever existed.** I found no evidence of one. Given OpenAI's own "outside SOC 2/ISO scope, enterprise controls may not apply" language, it is very unlikely Atlas browsing was ever inside a BAA's scope, even for Enterprise. Atlas no longer exists, and the HIPAA status of the successor desktop-app browser was not found (see Gaps).
- [INFERRED] **If staff opened EHR, patient-portal, insurance-portal or scheduling screens in Atlas** with the sidebar, browser memories or agent mode on, page content (names, DOBs, diagnoses, appointment data) could have been sent to OpenAI. With no BAA, that is likely an impermissible disclosure under HIPAA. It needs a privacy-officer review and possibly a breach risk assessment. The danger is highest on a Business workspace, where Atlas was on by default with no admin opt-in.
- [INFERRED] **Website analytics:** the 2024 ruling took away OCR's position on *unauthenticated* public pages. It did not make third-party ad pixels (Meta/Google) on *authenticated* areas (patient portal, booking with PHI) acceptable without a BAA. Self-hosted, cookieless analytics (Umami in RootBiz's stack) keeps visitor data off ad networks and away from vendors without a BAA, which is the conservative choice for a clinic. Umami's cookieless design is stated in the assignment and was not separately verified in this session.
- [INFERRED] A DIY AI workflow also tends to leak PHI indirectly. Staff paste patient emails or testimonials into ChatGPT to "write a review page", or put real patient names into commit messages or repo issues.

### Gaps
- I could not reach OpenAI's primary BAA help article to confirm exactly which products are eligible as of Oct 2026, including whether the ChatGPT desktop app's Work browser or "ChatGPT for Healthcare" covers browsing.
- I found nothing showing that any clinic or OCR enforcement action specifically involved Atlas or AI browsers.
- I did not research Utah state privacy law (e.g. the Utah Consumer Privacy Act, which largely exempts HIPAA-covered data) in this session.

## 4. GitHub side: common mistakes in DIY GitHub-hosted sites, GitHub Pages limits and terms, secret scanning, push protection, branch protection

### Takeaway
GitHub Pages is a free static host with explicit limits (1 GB site, 100 GB/month soft bandwidth, 10 builds/hour soft) and a usage policy that it is "not intended for or allowed to be used as a free web-hosting service to run your online business". It also bars sensitive transactions such as passwords or card numbers. Secret leaks in public repos are common and growing: 28.65M new secrets leaked in public GitHub commits in 2025, and AI-assisted commits reportedly leak at about twice the baseline rate. GitHub's default push protection only stops known token patterns. Branch protection is not available for **private** repos on GitHub Free. A DIY clinic repo is therefore often either public (exposing everything in it) or private but unprotected, where whoever has access, AI agent included, pushes straight to the live site.

### Cited Findings
- [CONFIRMED] **GitHub Pages usage policy (verbatim fragment):** GitHub Pages is "not intended for or allowed to be used as a free web-hosting service to run your online business". The same sentence goes on to cover e-commerce sites and sites primarily directed at facilitating commercial transactions or providing commercial SaaS (paraphrased from the search summary). Pages sites "shouldn't be used for sensitive transactions like sending passwords or credit card numbers." — [GitHub Docs: GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- [CONFIRMED] **Pages limits:** one user or organization site per account; source repo recommended at 1 GB or less; published site no larger than 1 GB; deployments time out after 10 minutes; soft bandwidth limit of 100 GB/month; soft limit of 10 builds/hour (does not apply to custom Actions workflows). If a site goes over, GitHub may stop serving it or ask the owner to use a CDN or move hosts. — [GitHub Docs: GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- [CONFIRMED] **Push protection:** user-level push protection is on by default and blocks pushing *supported* secrets to public repos on GitHub.com (rollout began 2024-03-01). Repository-level push protection needs GitHub Secret Protection and is off by default. By default, anyone with write access can bypass it by giving a reason. A repo-level bypass creates an alert and an audit-log entry. — [GitHub Docs: Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection); [ITPro](https://itpro.com/software/open-source/everything-you-need-to-know-about-githubs-new-push-protection-changes)
- [REPORTED] GitHub secret scanning covers more than 200 token types from 180+ providers. GitGuardian says push protection only catches specific or prefixed secret types and has no historical scanning. Generic passwords, SMTP credentials or custom form keys can get through. — [ITPro](https://itpro.com/software/open-source/everything-you-need-to-know-about-githubs-new-push-protection-changes); [GitGuardian blog](https://blog.gitguardian.com/github-push-protection-enhancing-open-source-security-with-limitations-to-consider)
- [CONFIRMED / vendor report] **GitGuardian "State of Secrets Sprawl 2026"** (published Mar 2026, data for 2025):
  - **28.65 million** new hardcoded secrets in public GitHub commits in 2025, up 34%, the largest jump yet.
  - **1,275,105** leaked AI-service secrets, up 81%.
  - Leaked secrets up 152% since 2021, against 98% growth in GitHub's developer base.
  - 32.2% of internal repos and 5.6% of public repos hold at least one hardcoded secret.

  — [The Hacker News, Mar 2026](https://thehackernews.com/2026/03/the-state-of-secrets-sprawl-2026-9.html); [GitGuardian on DEV](https://dev.to/gitguardian/the-state-of-secrets-sprawl-2026-ai-service-leaks-surge-81-and-29m-secrets-hit-public-github-2bgj); [HackerNoon](https://hackernoon.com/gitguardian-reports-an-81percent-surge-of-ai-service-leaks-as-29m-secrets-hit-public-github)
- [REPORTED, lower-quality source] A summary of the same report says AI-assisted commits on public GitHub leaked secrets at about **3.2%**, against a **1.5%** baseline for human-only commits. — [Vibe Graveyard](https://vibegraveyard.ai/story/gitguardian-secrets-sprawl-ai-code-leak-study/)
- [CONFIRMED] **Branch protection:** available for public repos on GitHub Free and Free for organizations. For **private** repos it needs GitHub Pro, Team or Enterprise. One community thread asks GitHub to make basic protection free for private repos, and one third-party tool page claims otherwise, which contradicts the docs. — [GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [GitHub Community #174419](https://github.com/orgs/community/discussions/174419); [GitHub Community #72725](https://github.com/orgs/community/discussions/72725)

### Inferences
- [INFERRED] **Is a clinic site allowed on Pages?** An informational clinic brochure site is not "primarily directed at facilitating commercial transactions", so it is probably allowed. But it is the marketing site of a for-profit business, which sits close to "run your online business". Add any of the following and it is clearly against policy and the "sensitive transactions" warning: online payments, an intake form collecting health details, or a patient login. This is a gray area to flag, not a clear violation.
- [INFERRED] **No server-side code:** Pages serves static files only. GitHub describes it as a static site host. Everything dynamic (contact or intake forms, booking, chat) must go to third-party endpoints. DIY sites often embed form-service IDs, webhook URLs or API keys directly in the HTML or JS of a public repo. Anyone can then read and abuse them (spam or harvest the form), and any PHI sent through those forms reaches a vendor that may have no BAA.
- [INFERRED] **Typical DIY failure set**, from the sources above plus common practice:
  - Public repo by default, so drafts, staff emails, form keys and any `.env` that got committed are world-readable, and git history keeps them after deletion.
  - No branch protection on a free private repo, so whatever is pushed to `main` (by a person or an AI agent) goes live with no review.
  - No CI checks (build, links, accessibility, HTML validation).
  - No staging or preview, so changes are tested in production.
  - A single owner account, often a staff member's personal GitHub, with no 2FA enforcement and no handover plan. The clinic may not legally control its own site.
  - No changelog beyond terse AI-written commit messages.
- [INFERRED] An AI browser agent driving GitHub's web UI makes this worse. It can create commits, change Pages and DNS settings, or paste secrets into files without any terminal hook catching them. Push protection only catches known token formats.

### Gaps
- I could not retrieve GitHub's general Terms of Service text on commercial use (beyond the Pages limits page).
- I found no study counting how often small-business or clinic sites on Pages leak form endpoints or PHI.
- Whether GitHub Free's newer "rulesets" for private repos changed in 2026 was not confirmed. The docs found still say private-repo protected branches need Pro or Team.

## 5. Quality issues of AI-generated websites: accessibility, generic or hallucinated copy, local SEO schema, YMYL/E-E-A-T, missing analytics and monitoring

### Takeaway
Small, vendor-funded audits find AI-built sites fail basic accessibility. In one test all 15 AI-built sites failed WCAG Level A, averaging 55 issues per page. The broader web is also poor, with 95.9% of top homepages failing in WebAIM's scan. Google treats health as YMYL, and its rater guidelines (Sept 2025) give the lowest rating to content that is "all or nearly all" AI-generated with little added value. For a clinic, the main AI-copy risks are generic, interchangeable text and invented facts: services, credentials, insurance plans or languages that are not real. These hurt trust and rankings and can create legal exposure. Medical structured data (MedicalClinic/Physician JSON-LD) and monitoring are usually missing unless someone puts them in on purpose.

### Cited Findings
- [REPORTED, vendor-sponsored] **AudioEye / VentureBeat:** five AI tools were each asked to build accessible WCAG AA sites. **All 15 sites failed WCAG Level A**, averaging **55 issues per page**, and 91% of issues were medium or high severity. — [VentureBeat (presented by AudioEye)](https://venturebeat.com/ai/we-asked-five-ai-tools-to-build-accessible-websites-all-15-sites-failed)
- [REPORTED, vendor-sponsored] accessiBe audited two Lovable-built storefronts and found 24 issues, 8 of them critical. A syndicated Stacker piece reports AI-built stores averaging 174 issues per page. — [accessiBe report](https://accessibe.com/accessibility-platform/reports/gen-ai-ecommerce/accessibility-audit); [Stacker via The Garden Island](https://www.thegardenisland.com/syndicated/study-ai-coding-tools-do-not-write-accessible-code)
- [REPORTED, vendor survey] 81% of respondents were confident their AI-generated code met accessibility standards, yet 46% had received an accessibility complaint, demand letter or lawsuit. — [Stacker via The Garden Island](https://www.thegardenisland.com/syndicated/study-ai-coding-tools-do-not-write-accessible-code)
- [REPORTED] WebAIM's automated scan of one million homepages found failures on **95.9%** of them, and some coverage blames part of the worsening on AI-assisted coding. GreenGeeks cautions that this is a baseline for the whole web, not a comparison of AI-built and human-built sites. It also cites an Axess Lab case of a site with a perfect automated score that still failed a screen-reader user (focus trapped behind menus and dialogs). — [GreenGeeks](https://www.greengeeks.com/blog/?p=53300)
- [REPORTED] **Google Search Quality Rater Guidelines, Sept 2025 version:** YMYL covers topics that could "potentially impact people's health, financial stability, or safety". "If all or nearly all of the main content is auto- or AI-generated (with little or no added value), raters should apply the lowest rating". Using generative AI does not by itself decide quality. The January 2025 rater update added "scaled content abuse", "site reputation abuse" and "expired domain abuse" as spam types. — [iPullRank](https://ipullrank.com/eeat-ymyl-ai-search); [Semrush](https://www.semrush.com/blog/google-expands-rules-on-low-value-content); [SEO Kreativ](https://www.seo-kreativ.de/en/blog/google-quality-raters-update_9-25/)
- [REPORTED, SEO-vendor guides] Schema.org's healthcare types include **MedicalClinic** and **Physician** (with LocalBusiness patterns). Useful properties include address, telephone, opening hours, medicalSpecialty, availableService and identifiers such as the US NPI. Vendors claim this markup helps Google link the practice and its doctors to the Knowledge Graph, but those claims are unverified. One sample uses "PhysiciansOffice", which should be checked against schema.org. — [Ulement](https://ulement.com/medical-schema-markup/); [Hill Web Creations](https://www.hillwebcreations.com/physician-schema-markup/); [JSONLD.com](https://jsonld.com/physician-office/)

### Inferences
- [INFERRED] **Hallucination risk is specific to clinics.** An LLM asked to "write a services page for a family clinic in Taylorsville, Utah" will fill gaps with plausible content: services not offered, board certifications, "most insurance accepted", named insurers, Spanish-speaking providers, same-day appointments, years of experience. Each false item is a YMYL trust failure and a likely source of patient complaints or front-desk friction. Some (credentials, insurance participation) may create consumer-protection or medical-board exposure. Every factual claim needs sign-off by the clinic.
- [INFERRED] **Generic copy and duplicate content:** AI copy for "clinic in [city]" pages comes out near-identical across sites and across city or service pages. That matches what Google's guidelines downgrade ("little or no added value") and offers no Experience signal (real provider bios, photos, credentials, NPI-linked Physician markup).
- [INFERRED] **Bilingual sites:** a DIY AI site often machine-translates Spanish pages without proper `hreflang`, separate URLs or human review of medical terms. RootBiz's bilingual Astro build should be judged on separate localized URLs, `hreflang` pairs, a medically reviewed translation, and localized schema. Not separately sourced in this session.
- [INFERRED] **Missing operations layer:** DIY sites typically have no analytics, no uptime monitoring, no form-delivery checks, no broken-link checks and no Search Console. A contact form that quietly stops delivering, an expired domain or a broken booking link can go unnoticed for weeks.

### Gaps
- I found no peer-reviewed or neutral (non-vendor) study of AI-built *small-business* or *medical* websites. All the accessibility figures come from vendors who sell accessibility products and use small samples.
- I found no study measuring how often AI-written business sites contain hallucinated factual claims (services, credentials, insurance).
- I did not retrieve Google Search Central's own docs on LocalBusiness or medical structured data eligibility. Google has no clinic-specific rich result that I could confirm.
- The edition year of the WebAIM Million figure (95.9%) was not confirmed from the primary source.

## 6. What a structured professional maintenance process looks like (RootBiz stack) vs. the DIY GitHub + AI-browser process

### Takeaway
A professional process puts controls in the path between "someone (or some AI) proposes a change" and "it goes live":
- branch-based work with preview deploys behind authentication
- human code review with protected branches
- automated checks
- secret scanning
- uptime monitoring
- backups
- dependency updates
- privacy-safe analytics
- a change log
- shared credential management with 2FA
- domain, DNS and accounts legally owned by the client

The RootBiz stack (Astro on Cloudflare Pages/Workers with Access/Tunnel, GitHub, self-hosted n8n, Twenty CRM, Chatwoot, Umami, Uptime Kuma, Vaultwarden, Nextcloud, Ollama) covers each of these. AI can still be used, but as a drafting tool whose output a person reviews, not as an autonomous agent logged into production accounts.

### Cited Findings
- [CONFIRMED] **Preview deploys and gating them:** Cloudflare Pages builds a preview deployment per branch or commit with its own URL. Cloudflare says restricting access to previews with Cloudflare Access is "as easy as clicking a button". By default, members of the Cloudflare organization get an emailed one-time PIN, and SSO can be used instead. Cloudflare's announcement says Access includes **50 seats on the free tier**. That figure comes from older material, so check the current plans page. — [Cloudflare blog: Pages GA](https://blog.cloudflare.com/cloudflare-pages-ga)
- [REPORTED] Pages preview URLs (hash-based) stay reachable until the deployment is deleted, so previews should sit behind Access, for example with a wildcard policy on `*.project.pages.dev`. (2026-05-13 walkthrough citing Cloudflare docs.) — [israynotarray blog](https://israynotarray.com/en/misc/2026/05/13/cloudflare-pages-preview-urls-stay-forever-lock-with-access/)
- [CONFIRMED] **Protected branches** (required reviews, required status checks, no direct pushes) are available on public repos with Free and on private repos with Pro, Team or Enterprise. — [GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- [CONFIRMED] **Secret controls:** repository-level push protection (via GitHub Secret Protection) is off by default and must be turned on. Bypasses create alerts and audit-log entries. GitHub Team and Enterprise organizations can run a free secret-risk report. — [GitHub Docs: Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection)
- [CONFIRMED / secondary] **Agentic-AI controls to copy into an agency's own AI use:** treat external content as untrusted, give agents the least access needed, and require human approval for irreversible operations. (OWASP Agentic Top 10, Dec 2025.) — [HUMAN Security](https://www.humansecurity.com/learn/blog/owasp-top-10-agentic-applications/); [Cycode](https://cycode.com/blog/owasp-top-10-agentic-applications/)
- [CONFIRMED] **OpenAI's own guidance** keeps agents out of logged-in sessions except for "well-scoped actions on very trusted sites". Gartner advises enterprises to block AI browsers and limit credential sharing. — [Simon Willison quoting OpenAI CISO](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/); [The Register](https://www.theregister.com/2025/12/08/gartner_recommends_ai_browser_ban/)

### Inferences
- [INFERRED] **Side-by-side comparison** (built from the findings in Q1 to Q6; the RootBiz components come from the assignment brief and were not independently verified):

| Area | DIY "GitHub + ChatGPT Atlas" (or its 2026 successors) | Structured agency process (RootBiz stack) |
|---|---|---|
| Tool status | Atlas shut down 2026-08-09; macOS only; never on Windows | Stable, version-pinned toolchain (Astro, GitHub, Cloudflare) |
| Who changes production | An AI agent clicking in a logged-in browser; often pushes straight to `main` | Changes on branches, reviewed in a PR, merged by a person; protected `main` |
| Testing before live | None. Atlas agent couldn't run builds or code | Cloudflare Pages preview URL per branch, behind Cloudflare Access; CI build, link and a11y checks |
| Security of accounts | Agent holds GitHub, registrar, GBP and possibly EHR sessions; prompt injection "unlikely to ever be fully solved" | Least-privilege roles, enforced 2FA, shared vault (Vaultwarden), no AI agent in admin sessions; Cloudflare Access/Tunnel for internal tools |
| Secrets | Easily committed to public repos; default push protection only catches known patterns | Secrets in Cloudflare/Workers env vars; repo push protection on; private repo |
| PHI / privacy | No BAA for consumer or Business ChatGPT; Atlas outside SOC 2 scope; staff may browse EHR in the AI browser | Self-hosted chat (Chatwoot), CRM (Twenty), automation (n8n) and local AI (Ollama), so data stays on infrastructure the agency or clinic controls; still needs a clinic-approved policy, a BAA where any vendor touches PHI, and no PHI in website forms unless covered |
| Forms / dynamic features | GitHub Pages is static; third-party form keys exposed in HTML | Cloudflare Workers / n8n endpoints with server-side validation, spam protection, routing to CRM or inbox |
| Analytics | Often none, or Google/Meta pixels (tracking-tech risk) | Umami (self-hosted, cookieless per brief); no ad pixels on sensitive pages |
| Monitoring | None; outages and broken forms go unnoticed | Uptime Kuma checks for site, forms, SSL expiry, domain expiry; alerts |
| Backups and continuity | Single personal GitHub account; lost Atlas data at shutdown | Git history plus off-platform backups (Nextcloud); documented restore |
| Content quality | Generic, possibly hallucinated claims; weak a11y; no schema | Facts confirmed by clinic sign-off; bilingual human review; MedicalClinic/Physician JSON-LD; WCAG checks |
| Change log | Terse AI commit messages | PR descriptions plus a client-facing change log; monthly report |
| Ownership | Domain, GBP and GitHub may sit in a staff member's personal accounts | Client owns registrar, DNS (Cloudflare), GBP and GitHub org; agency gets delegated, revocable access |

- [INFERRED] **Recommended maintenance cadence for a clinic site:**
  - Monthly: dependency updates (Renovate/Dependabot or manual Astro bumps) shipped through preview, accessibility and Lighthouse checks, uptime and SSL report, Umami traffic summary, GBP check (hours, phone, holiday hours).
  - Quarterly: access review (remove ex-staff, rotate keys), backup restore test, content-accuracy review with the clinic (services, providers, insurance list).
  - Yearly: domain renewal check and privacy-policy review.

  This is normal industry practice; no specific source for the cadence.
- [INFERRED] **How AI fits professionally:** use a local model (Ollama) or an approved vendor to *draft* copy and code. A person reviews every PR, and the clinic signs off on every medical or business fact. No AI agent ever holds production credentials. This follows the OWASP "least agency / human approval" principle and OpenAI's own logged-out guidance.
- [INFERRED] For the audit narrative: the DIY process is not cheaper once you count the risks. These include a single domain or GBP hijack, a PHI disclosure without a BAA, an ADA demand letter (46% of AI-site owners in the vendor survey had received a complaint, letter or lawsuit), or weeks of silent form failure. Each costs more than a year of managed maintenance. This is a qualitative argument; no cost study was found.
